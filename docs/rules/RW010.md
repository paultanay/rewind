# RW010 — Alert-as-symptom corroboration

**Status:** Implemented (Phase 4)  
**Confidence potential:** Corroboration only (never trigger)

## Pattern

`AlertFired` events **never** score as causal triggers. They are treated
as corroborating evidence for other hypotheses when they temporally overlap.

## Rationale

Alerts are produced by monitoring systems *after* a condition has been
ongoing long enough to cross a threshold. By definition, an alert cannot
cause the incident it is alerting on. Treating alerts as root causes is a
common cognitive trap in incident response that this rule explicitly prevents.

The correct mental model: alerts are symptoms. They confirm an anomaly is
real and significant, but the trigger lies earlier in the timeline.

## Scoring

- `AlertFired` events contribute **+0.1** to the score of any hypothesis
  whose time window overlaps with the alert's firing time.
- The contribution is capped at +0.2 per hypothesis (two alerts maximum).
- `AlertResolved` events are recorded in the timeline but have no effect on
  hypothesis scoring.

## Example

```
14:18:00  Deploy    checkout v2.3.1         ← candidate trigger
14:20:40  Anomaly   latency.p99 ↑4.2×      ← RW001 fires
14:22:00  AlertFired  HighLatency            ← corroborates RW001 hypothesis (+0.1)
14:22:30  AlertFired  ErrorRateHigh          ← corroborates RW001 hypothesis (+0.1, capped)
```

Result: RW001 hypothesis score increases by 0.2. HighLatency alert is listed
as "corroborating evidence" in the Hypothesis explanation.

## Why this design matters

Without this rule, naive scoring engines produce verdicts like:
*"most likely cause: HighLatency alert fired (confidence: high)"* — which
is technically wrong and actively unhelpful during an incident.

Rewind's verdict template always marks alerts as corroboration, never as
the primary finding, making the distinction visible to any reader.
