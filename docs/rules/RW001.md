# RW001 — Deploy-triggered anomaly

**Status:** Implemented (Phase 4)  
**Confidence potential:** High

## Pattern

A `Deploy` event on an entity is followed by one or more metric change-points
on the same entity or its direct graph-adjacent dependents within a 10-minute
window.

## Rationale

Deployments are the most common root cause of production incidents. This rule
encodes the basic temporal pattern: "something changed, then something broke."
The 10-minute window is intentionally conservative — most deployment-related
failures manifest within 2–5 minutes (traffic cut-over, JVM warm-up, health
checks), but memory leaks and slow-rolling traffic patterns can take longer.

## Scoring table

| Gap (deploy → change-point) | Base score |
|---|---|
| 0–2 minutes | 0.9 |
| 2–5 minutes | 0.6 |
| 5–10 minutes | 0.3 |
| > 10 minutes | rule does not fire |

## Confidence upgrade

- +High if ≥3 corroborating signals on the same entity
- +High if `error.rate` change-point is one of the corroborating signals
- Downgraded to Medium if a competing hypothesis is within 20% of score

## Interaction with other rules

- RW002 is the ConfigChange analogue of this rule
- RW003 supersedes RW001 when an OOMKill chain is present
- RW010 (alert-as-symptom) may corroborate this rule's score

## Implementation notes

The deploy event comes from the CI/CD collector (GitHub/GitLab) and/or the
Kubernetes rollout reconstruction. The entity graph ensures we match deploys
to their service-level change-points via the `pod → deployment → service`
ownership chain.

## Example

```
14:20:00  Deploy   checkout v2.3.1
14:20:40  Anomaly  latency.p99 ↑4.2×    [gap: 40s → score: 0.9]
14:21:00  Anomaly  error.rate ↑8.1×     [corroboration +High]
14:21:15  OOMKill  checkout-7d9f        [corroboration]
```

Result: RW001 fires with High confidence.
