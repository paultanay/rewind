# RW007 — Probe Failure → Restart Loop

**Status:** Implemented (Phase 4)
**Confidence potential:** Medium

## Pattern

`ProbeFailed` events (liveness or readiness probe timeouts) on a pod,
followed within 3 minutes by `Restart` events on the same pod.

## Rationale

Probe misconfiguration is a common cause of restart loops after a deploy:
the new version has a longer startup time, a blocking health-check handler,
or a regression in the probe endpoint. The pod is repeatedly killed and
restarted by kubelet without ever becoming healthy.

## Probe types detected

- **Liveness probe** failure → kubelet kills and restarts the container
- **Readiness probe** failure → pod removed from service endpoints (traffic cut)
  but not restarted unless liveness also fails

## Interaction with other rules

- RW001 (deploy) often precedes RW007 — the probe started failing after a deploy
- RW009 (crash loop) fires in parallel when restarts accumulate ≥3 in 10 minutes

## Configuration guidance

Common fixes: increase `initialDelaySeconds`, increase `timeoutSeconds`,
reduce `failureThreshold`, or add a `startupProbe`.

## Example

`
14:15:00  Deploy    api-server v1.8.0   (new version, longer startup)
14:16:30  ProbeFailed  api-server-6f7b  liveness timeout after 10s
14:16:40  Restart      api-server-6f7b  restart #1
14:18:30  ProbeFailed  api-server-6f7b  liveness timeout after 10s
14:18:40  Restart      api-server-6f7b  restart #2
`

Result: RW007 fires with MEDIUM confidence; probe failures named as trigger.
