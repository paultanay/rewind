# RW008 — Log Burst → Error Spike Correlation

**Status:** Implemented (Phase 5)
**Confidence potential:** Low (corroborating only)

## Pattern

A `LogBurst` event from Loki on an entity, correlated with a metric
`error.rate` change-point on the same entity within a 5-minute window.

## Rationale

Log bursts are symptoms, not causes. A spike in error-level log lines
confirms that something is wrong, but it does not tell us *why*. RW008
therefore acts as a corroborating rule: it adds evidence to an existing
hypothesis rather than creating a standalone trigger.

This is equivalent to a witness statement — it confirms the crime happened
at a certain time, but doesn't identify the perpetrator.

## Implementation note

RW008 is marked `CorroborationOnly: true` in the rule assembler. It can
never produce a standalone verdict. If no prior hypothesis matches the same
entity+window, RW008's score contribution is discarded.

## Log burst detection (Loki collector)

The Loki collector uses `count_over_time({...}[1m])` with a 3× baseline
threshold. Only error-level lines (`level=error`, `ERROR`, `FATAL`)
are counted. Sample lines are attached to the event for the web UI.

## Example

`
14:05:00  Deploy    checkout v2.3.1          ← RW001 trigger
14:07:00  LogBurst  checkout (12.3 err/s)    ← RW008 corroboration
           "ERR: connection pool exhausted"
           "FATAL: DB timeout after 30s"
14:08:00  Anomaly   error.rate ↑8×
`

RW008 adds +0.15 to the RW001 hypothesis score. RW001 retains the trigger.
