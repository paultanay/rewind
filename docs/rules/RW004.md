# RW004 — CPU Saturation → Latency Increase

**Status:** Implemented (Phase 4)
**Confidence potential:** Medium

## Pattern

A `cpu.usage` or `cpu.throttle` change-point ↑ on an entity, followed
within 5 minutes by a `latency.p99` change-point ↑ on the same entity.

The CPU change-point must strictly precede the latency change-point.

## Rationale

CPU saturation causes the OS scheduler to time-slice more aggressively,
increasing queuing delays for incoming requests. This is the classic
"CPU-starved process starts queuing requests" pattern.

The 5-minute window is tighter than RW001/RW002 because CPU→latency
causation is near-instantaneous: if CPU is throttled, latency rises within
seconds. A large gap suggests a different root cause.

## Scoring discount

Score is discounted by 0.5× when the CPU magnitude increase is < 50%.
Sub-saturation CPU changes rarely cause detectable latency degradation.

## Interaction with other rules

- RW001/RW002 supersede RW004 when a deploy or config change is present
- RW008 (scale event) may explain *why* CPU rose (under-provisioned)

## Example

`
14:10:00  cpu.throttle  recommendation  0.02 → 0.72 (change-point)
14:12:00  latency.p99   recommendation  95ms → 600ms (change-point)
`

Result: RW004 fires with SPECULATIVE confidence (no deploy event to confirm).
