# RW002 — Config Change → Metric Change-Point

**Status:** Implemented (Phase 4)
**Confidence potential:** High

## Pattern

A `ConfigChange` event on an entity is followed by one or more metric
change-points on the same entity within a 15-minute window.

## Rationale

Config changes (feature flags, environment variables, quota updates, A/B
experiments) are the second most common root cause of production incidents.
They are treated separately from deploys (RW001) so that postmortems can
distinguish code changes from configuration changes — a critical distinction
when the same binary is running with different flags.

The 15-minute window is wider than RW001's 10 minutes because config changes
(especially feature flags with gradual rollout) often manifest more slowly.

## Scoring table

| Gap (config → change-point) | Base score |
|---|---|
| 0–2 minutes | 0.85 |
| 2–5 minutes | 0.55 |
| 5–15 minutes | 0.28 |
| > 15 minutes | rule does not fire |

## Interaction with other rules

- RW001 is the Deploy analogue; both can fire for the same entity
- RW010 (alert-as-symptom) may corroborate this rule's score

## Example

`
09:00:00  ConfigChange  feature-flag: new-payment-provider=true
09:08:00  Anomaly       error.rate ↑8×   [gap: 8m → score: 0.42]
09:10:00  AlertFired    HighErrorRate    [RW010 corroboration +0.10]
`

Result: RW002 fires with Medium confidence (corroborated by RW010).
