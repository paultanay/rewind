# RW009 — CrashLoop Detection

**Status:** Implemented (Phase 4)
**Confidence potential:** High

## Pattern

When ≥3 `Restart` events occur on the same pod entity within a 10-minute
sliding window, they are coalesced into a single synthetic `CrashLoop`
event at the timestamp of the first restart. The synthetic event is then
scored as a trigger candidate.

## Rationale

Kubernetes CrashLoopBackOff generates many individual Restart events that
are individually unremarkable but collectively indicate a serious failure.
Coalescing prevents the individual events from fragmenting the causal chain
into noise and gives the correlation engine a single, high-signal event to
work with.

The synthesised event is annotated with the restart count and the pod
name, making the verdict human-readable:
`CrashLoop: checkout-7d9f (4 restarts in 8m)`.

## Threshold

| Restarts in 10m | Action |
|---|---|
| 1–2 | Individual events kept; no coalescing |
| ≥3 | Coalesced into CrashLoop synthetic event |

## Interaction with other rules

- RW003 (OOMKill) often precedes RW009 — OOMKills cause the crash loop
- RW007 (probe failure) often precedes RW009 — probe failures cause restarts
- RW001/RW002 may have caused the initial failure that led to the loop
- RW005 (upstream cascade) may fire on downstream services during the loop

## Example

`
14:08:00  OOMKill   checkout-7d9f  (RW003 trigger)
14:09:00  Restart   checkout-7d9f  restart #1
14:11:00  Restart   checkout-7d9f  restart #2   ← exponential back-off
14:13:00  Restart   checkout-7d9f  restart #3   ← coalesced here
`

Synthetic event: `CrashLoop: checkout-7d9f (3 restarts in 4m)` at 14:09:00.
RW009 scores the CrashLoop as HIGH confidence trigger for downstream errors.
