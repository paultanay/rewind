# RW008 - Scale Down to Saturation

**Status:** Implemented
**Confidence potential:** Medium

## Pattern

A scale-down event is followed by an upward CPU or latency change-point on the
same entity within 5 minutes. The rule currently requires replica-signal
evidence showing a downward change-point around the scale event.

## Evidence required

- A Kubernetes or other source event classified as `ScaleChange`.
- A `replicas` change-point in the downward direction near that event.
- An upward `cpu.usage` or `latency.p99` change-point after the event.

The rule models reduced capacity as a possible contributor. It does not claim
that scaling caused the incident when traffic, deployment, or dependency
evidence points elsewhere.

## Operational interpretation

Check HPA decisions, desired versus available replicas, request volume,
resource limits, and whether the scale-down was itself a response to an
earlier failure.

## Example

```text
14:05:00  ScaleChange: checkout reduced from 6 to 3 replicas
14:07:00  cpu.usage change-point: 2.4x on service/shop/checkout
           RW008: reduced capacity preceded saturation
```
