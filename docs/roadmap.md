# Rewind Roadmap

Items here are out of scope for v1.0. They have been deliberately deferred
to keep the initial implementation buildable, correct, and focused. Each item
has a brief rationale for *why* it was deferred — not just *that* it was.

---

## v2 candidates

### Continuous "flight recorder" mode

A long-running agent/daemon that records a rolling window of events and
signals so that investigations can start immediately after an incident, even
before a window is known.

Deferred because: it requires persistent storage, an agent deployment model,
and careful resource budgeting. These are significant operational concerns
that don't belong in v1's scope ("single static binary, no server to deploy").

### LLM-powered narrative layer

Natural language explanations of incidents, generated by an LLM using the
structured Verdict as input.

Deferred because: deterministic, explainable verdicts come first (v1). The
`Verdict` and `Hypothesis` types are designed with this extension in mind —
the `Explanation` field is currently template-generated, not free-form.
An LLM renderer can be added as `internal/render/llm` without touching the
analysis engine.

### Multi-incident storage server

A shared server that stores and indexes bundles, enabling team-wide search
and comparison across incidents.

Deferred because: this is a fundamentally different operational model (server
to deploy, database to run, RBAC to implement). v1's "state lives in bundle
files" principle must be proven first.

### RBAC and multi-user support

Access control for the web UI and API.

Deferred pending the storage server above.

### Elasticsearch / OpenSearch support

Log collector for teams not using Loki.

Deferred to Phase 7+. The Collector interface is designed to accommodate it.

### eBPF-based network topology

Automatic service-to-service dependency graph from kernel-level network
tracing, without requiring Tempo or manual configuration.

Deferred because: requires root/privileged access, which conflicts with the
"safe to run mid-incident" principle. When added, it will be an opt-in
collector with explicit privilege documentation.

### Auto-remediation

Automated responses to detected incidents (e.g. rollback on high-confidence
Deploy verdict).

**Will not build.** Auto-remediation is dangerous without deep operational
context that Rewind intentionally does not have. The product proposes;
the engineer decides.

## Known limitations to document

- Prometheus staleness markers are not handled as change-points (series that
  disappear before the window ends are treated as zero-value, which can
  inflate magnitude calculations).
- Multi-cluster investigations require running rewind once per cluster and
  merging bundles manually (no bundle merge command yet).
- The 10-minute deployment correlation window (RW001) may produce false
  positives in environments with very frequent deploys.
