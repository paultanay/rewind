# RW003 — OOMKill Evidence

**Status:** Implemented (Phase 4)
**Confidence potential:** High

## Pattern

`memory.usage` change-point ↑ on an entity → `OOMKill` event on the
same entity → `Restart` event(s) → `error.rate` ↑ on the entity or its
downstream dependents.

## Rationale

OOMKills are among the clearest causal chains in production: memory rises,
the OOM killer fires, the container restarts with an error window. When all
four steps are present the causal chain is nearly unambiguous. Missing steps
reduce confidence proportionally.

The memory rise check (10 minutes before OOMKill) distinguishes genuine OOM
events from external kills (`kubectl delete pod`).

## Confidence levels

| Chain present | Confidence |
|---|---|
| memory ↑ + OOMKill + Restart + error.rate ↑ downstream | HIGH |
| OOMKill + Restart + error.rate ↑ (no memory signal) | MEDIUM |
| OOMKill only | SPECULATIVE |

## Interaction with other rules

- RW009 (crash loop) may fire if OOMKills repeat ≥3 times in 10 minutes
- RW005 (upstream cascade) may fire on the downstream service
- RW001 may fire if the OOMKill was itself caused by a bad deploy

## Example

`
14:00:00  memory.usage  checkout  55% → 91% (8 min rising trend)
14:08:00  OOMKill       checkout-7d9f-xk2p9   limit=512Mi used=511Mi
14:09:00  Restart       checkout-7d9f-xk2p9   restart #1
14:11:00  Anomaly       error.rate ↑23×  (downstream: frontend)
`

Result: RW003 fires with HIGH confidence.
